## Selenium vs Playwright

> For a new modern web automation project, I usually prefer Playwright because of stability, auto-waiting, tracing, parallel execution, and CI diagnostics.
>
> Selenium is still a strong choice in mature enterprise ecosystems, especially when the organization already has a large Selenium stack.
>
> I'm comfortable with both, and I'd choose based on existing architecture, team skills, and product constraints.

## Framework from scratch

> I would start by clarifying testing layers, risks, CI expectations, environments, and ownership.
>
> Then I'd define structure: test runner, page/component objects or screen-level abstractions, API helpers, test data strategy, reporting, retries policy, parallelization, and coding standards.
>
> I'd keep the framework small at first, prove it on critical flows, then expand with patterns that the whole team can maintain.

## Flaky tests

> I usually investigate flakes by separating product issue, test issue, environment issue, and data issue.
>
> Then I look at waits, async behavior, test isolation, shared state, unstable dependencies, and CI resource constraints.
>
> Good diagnostics matter: traces, screenshots, videos, console/network logs, and clear failure messages.

## Quality metrics

> I'd avoid vanity metrics like just total test count.
>
> Better metrics are pass-rate stability, flaky rate, defect leakage, critical-flow coverage, execution time, time to diagnose failures, and how often automation catches real regressions before release.
