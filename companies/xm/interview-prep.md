### Describe a difficult automation problem.

> At Definely, one problem was that automation output was too noisy. The pipeline produced around 1.5 GB of logs per run, which made failures hard to investigate. I reviewed what was actually useful for debugging, removed unnecessary debug logging, and reduced output to around 11 MB per run. At the same time, coverage increased from around 117 to 199 tests without increasing runtime. The lesson was that automation quality is not only about more checks; it is also about signal quality and maintainability.

### How would you design an API automation framework?

> I would start with the product risks and the test layers we need: contract/schema checks, functional flows, negative cases, data validation, and maybe performance checks.
>
> Then I would define a small maintainable framework structure: API clients, test data builders, fixtures, environment configuration, authentication helpers, assertions, reporting, logging, and CI integration.
>
> I would keep tests readable and independent, avoid hidden shared state, make failures easy to diagnose, and expand coverage around critical flows first.

### How do you test REST APIs?

> I look at status codes, response schema, business rules, authorization, validation, error handling, boundary values, state changes, database effects where relevant, and integration with downstream systems.
>
> I also care about test data setup and cleanup, correlation IDs/logs for debugging, and whether failures produce enough information to identify root cause quickly.

### How do you reduce flaky tests?

> First I classify the flake: product issue, test issue, environment issue, dependency issue, or data issue. Then I check waits/timing, shared state, test isolation, unstable data, asynchronous processing, retries, and CI resource constraints.
>
> I prefer fixing the root cause over hiding failures with retries. Retries can be useful only when they are measured and visible.

### How do you approach performance testing?

> I start by clarifying the goal: baseline, regression detection, capacity, latency under load, or bottleneck investigation. Then I define realistic scenarios, data, metrics, and thresholds.
>
> For API/backend systems I would watch latency percentiles, throughput, error rate, resource usage, logs, and downstream dependencies. For CI, I would keep performance checks targeted so they can catch regressions without becoming too expensive or noisy.

### How would you test a Forex brokerage core?

> I would focus on correctness, timing, resilience, and traceability. Example areas: order/request validation, account state, balances/margins where applicable, pricing/quotes, execution lifecycle, rejects/errors, boundary values, concurrency, retries, idempotency, audit logs, and monitoring.
>
> Since I am not a Forex domain expert yet, I would pair closely with product/business specialists to identify the most critical flows and domain-specific edge cases.

### How do you work with developers?

> I prefer close cooperation: clarify acceptance criteria early, discuss testability, review logs and failure patterns together, and make automation feedback actionable. I do not want QA to be a late gate only; I want quality work to be part of the development cycle.

### What do you do when requirements are unclear?

> I turn ambiguity into concrete examples. I ask about expected behavior, edge cases, error handling, data constraints, and business risk. If needed, I propose test scenarios and confirm them with the product owner or developer before automating.

## Technical Topics To Review Before The Call

- Python basics for test automation: pytest-style fixtures, parametrization, assertions, requests/httpx, typing basics, virtual environments.
- REST API testing: auth, schema validation, negative tests, state transitions, logs/correlation IDs.
- Async/multithreading: race conditions, eventual consistency, timeouts, polling strategy, thread/process safety at a high level.
- WebSockets: connection lifecycle, subscriptions, message schema, reconnects, heartbeats, ordering.
- Kafka testing: topics, producers/consumers, offsets, consumer groups, retries, idempotency, correlation IDs.
- Docker: containerized test environments, test dependencies, logs, networking basics.
- Grafana/monitoring: dashboards, metrics, logs, traces, alerting signals, using monitoring to investigate failures.
- Performance testing: baseline, thresholds, percentiles, throughput, error rate, bottleneck investigation.
